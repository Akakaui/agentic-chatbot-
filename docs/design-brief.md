# Lattice design brief

## Product position

Lattice is a conversation-first agent workspace for people who want an assistant that can research, plan, delegate, ask for decisions, use approved remote tools, and produce durable artifacts without exposing arbitrary machine-level execution.

## Primary users and tasks

| User | Primary task | What they need to understand | Success signal |
|---|---|---|---|
| Individual operator | Ask a standalone question or delegate a multi-step goal | Whether the assistant is answering, researching, waiting, or blocked | A useful answer or clear next action appears without navigating an admin surface. |
| Project owner | Group conversations, sources, instructions, and artifacts | Which context is active and what memory boundary applies | The assistant uses the intended project knowledge and the user can inspect or change it. |
| Tool administrator | Connect or remove remote MCP servers and set approval behavior | Which tools can read, write, or require confirmation | A connector can be configured, tested, scoped, and disabled without hidden side effects. |
| Agent builder | Define primary/subagents and assign skills or models | Which agent is active and how delegation is governed | A run shows understandable delegation and the user can inspect the decision path. |

## Information architecture

The product has four layers. **Conversation** is the default and must remain visually dominant. **Workspaces** contain projects, sources, agents, skills, schedules, connectors, and memory. **Artifacts** are durable work products generated by a conversation and open in a dedicated canvas. **Settings** govern provider models, profile, appearance, permissions, and safety.

The desktop shell uses a slim rail plus a top context bar. The mobile shell uses a single surface at a time with a sheet or stack for navigation and artifacts. The app must never require a user to understand the entire agent architecture before sending a first message.

## Primary flows

| Flow | Trigger | Steps | Success | Recovery |
|---|---|---|---|---|
| Standalone chat | New conversation | Type, attach optional files, send, receive answer | Answer appears in a readable conversation | Retry, edit prompt, or start a new chat |
| Agentic run | Goal implies research, planning, tool use, or artifact work | Plan → act → compact activity → answer/artifact | User sees useful evidence and result | Pause, cancel, retry, or inspect blocked requirement |
| Question tool | Assistant lacks a necessary preference or decision | Assistant pauses → user answers one or more cards → run resumes | Choices are recorded and the run continues | Custom answer, change answer, cancel run |
| Project context | User chooses a project | Select project → review context badge → chat | Responses use project instructions and sources | Clear scope or move chat to another project |
| Artifact iteration | Assistant creates a durable output | Open render → inspect source/history → request change → new version | Artifact remains reusable and recoverable | Fix with assistant, restore version, download |
| Remote MCP action | Assistant proposes external read/write | Show tool name, target, permissions → approve if needed → execute | Audit event and result are visible | Deny, retry, disable connector |

## States required

The product must include first use, empty workspace, loading, streaming, partial success, question-required, approval-required, blocked capability, provider missing, connector disconnected, artifact render failure, stale model list, offline/local-only, deleted item, and undo/recovery states.

## Success criteria

A new user should be able to understand where to type within five seconds, identify whether the assistant is working or waiting, answer a clarification without losing their place, open an artifact without leaving the conversation, and recover from a failed tool or artifact render without starting over. At 390px wide, the user should not see a desktop sidebar squeezed into the chat.
